# H.Dev Studio 제작 과정 전체 트러블슈팅 기록

> 작성일: 2026-09-16.
> 정리 기준: 공개 노션 읽기 수정까지의 작업 대화, 저장소 소스, 변경 내역, 검증 기록.
> 범위: 티스토리 캡처 자동화 구상부터 Windows 앱, 공개 발행, 배포·Git 이력 정리, 말투 설정, 참고자료·공개 노션 읽기까지.

## 이 문서를 읽는 기준

실제로 발생한 오류와 기능을 만들면서 미리 막은 위험을 구분했다. 사용자 요청으로 바뀐 디자인·작업 방식도 별도로 기록했다.

- **발생·수정:** 작업 중 증상이나 오류를 관찰했고 수정한 항목.
- **설계·보강:** 기능 추가 또는 오류 예방을 위한 구현. 실제 사고가 있었다는 뜻은 아니다.
- **검증 제한:** 구현이나 일부 검사는 끝났지만 실제 사용 환경까지 확인하지 못한 항목.
- **사용자 결정:** 기술적 문제를 설명한 뒤 사용자가 선택한 유지·변경 사항.

과거 기록이 모두 남아 있는 것은 아니다. `0.2.0`은 소스가 없고, `v0.3.0`~`v0.3.4`는 남은 배포본에서 소스를 복원한 태그다. 복원 커밋 시각을 실제 개발 시각으로 해석하면 안 된다. 일부 초기 대화의 상세 실행 기록도 조회되지 않아, 확인할 수 없는 오류나 원인은 추정해서 추가하지 않았다.

현재 패키지 버전은 `0.4.0`이다. 참고자료와 공개 노션 읽기 개선은 이 문서 작성 시점에 **개발 소스의 Unreleased 변경사항**이며, 기존 `0.4.0` EXE에 이미 포함됐다는 뜻은 아니다.

## 1. 전체 흐름과 주요 문제

### 버전별 진행

| 단계 | 주요 작업 | 핵심 문제·대응 |
| --- | --- | --- |
| 초기 구상 | 캡처·메모를 모아 기존 말투로 초안 작성 | 로그인된 브라우저 편집기와 AI 분석을 연결하는 흐름 결정 |
| `0.2.0` | 사진 업로드, 메모, AI 초안, 편집·미리보기, 휴대용 EXE | 파일 중심 작업을 사용자가 조작할 수 있는 앱으로 전환 |
| `0.3.0` | 검토한 초안을 버튼 한 번으로 공개 발행 | 제출 내용 고정, 중복 발행 방지, 결과 불확실 상태 처리 |
| `0.3.1` | 실제 티스토리 사진·태그 입력 보완 | 사진은 올라갔는데 업로드 정보를 다시 읽지 못하는 오류 수정 |
| `0.3.2` | 자료 폴더 열기, 발행 결과 확인 보완 | Windows 실제 경로 문제, 발행 성공 후 실패 표시, 공개 주소 차이 대응 |
| `0.3.3` | 글별 용량 표시와 로컬 자료 전체 삭제 | 사진·초안·이력·발행 사본을 일관되게 정리하도록 구현 |
| `0.3.4` | 표지 선택·별도 업로드 | 중복 사진, 설명 유실, 재생성 시 선택 유실을 막도록 구현 |
| 이력·배포 정리 | 과거 소스 복원, 공개 저장소, 설정 분리 | 뒤섞인 과거 빌드, 개인 정보, 한글 경로와 삭제 잠금 문제 처리 |
| `0.4.0` | Codex/Claude 선택, 말투 설정, 사이드바, GitHub 색감, 오리 로고 | 개인 CLI 연결, 실제 이미지 전달, 개발·배포 앱 구분 |
| Unreleased | 사진 아래 참고자료, 자료 읽기, 공개 노션 본문 수집 | 빈 HTML, 여러 응답으로 나뉜 본문, 접힌 항목 누락 해결 |

### 가장 큰 배움

1. **사진 업로드 성공과 업로드 정보 추출 성공은 다른 단계다.** 티스토리 편집기의 실제 이미지 요소를 읽어야 했다.
2. **발행 버튼 실행 오류와 실제 게시 실패는 같지 않았다.** 공개 페이지에서 결과를 별도로 확인해야 했다.
3. **공개 URL이라고 단순 HTML 요청으로 본문이 나오는 것은 아니다.** 노션은 본문을 별도 요청으로 나눠 가져왔다.
4. **첫 응답이나 페이지 나누기만 처리해서는 문서 전체를 읽었다고 할 수 없었다.** 접힌 항목의 자식 내용까지 확인해야 했다.
5. **EXE가 남아 있다고 과거 개발 이력이 보존되는 것은 아니다.** 원본 배포본을 기준으로 소스를 복원하고 Git으로 관리해야 했다.
6. **테스트 통과의 범위를 명확히 해야 했다.** 가짜 편집기·가짜 AI 검사, 실제 공개 자료 읽기, 실제 사용자 글 발행은 서로 다른 검증이다.

## 2. 티스토리 사진 업로드·공개 발행

### T01. 임시저장 중심 구상에서 공개 발행까지 작업 범위가 바뀜

**구분:** 사용자 결정·설계 변경

- 초기에는 사진·메모로 초안을 만들고 티스토리 임시저장까지만 수행하는 흐름이었다.
- 이후 사용자가 앱에서 검토한 초안의 **티스토리에 발행** 버튼을 누르면 사진 업로드부터 공개 발행까지 진행하도록 요청했다.
- 이에 따라 버튼 클릭을 해당 초안의 발행 의사로 처리하고, 중간에 같은 의사를 다시 묻는 팝업을 추가하지 않도록 작업 규칙과 구현을 맞췄다.
- 공개 글 목록 조회와 로그인된 편집기 조작은 분리했다. 읽기용 목록 조회가 가능하다고 글쓰기 권한이 확인된 것은 아니다.

**남긴 기준:** 실제 버튼 클릭이나 해당 글에 대한 명시적 요청 없이 백그라운드로 발행하지 않는다. 개발 검증을 위해 임의의 공개 테스트 글을 만들지 않는다. 임시저장을 명시적으로 요청한 작업은 임시저장까지만 한다.

### T02. 사진은 업로드됐는데 “업로드된 사진 정보를 읽지 못했습니다” 오류

**구분:** 발생·수정 / `0.3.1`

**증상:** 실제 편집기에 사진 한 장이 올라간 뒤 이미지 정보를 읽는 단계에서 중단됐다. 해당 시도는 최종 공개 발행 전이었다.

**원인:** 업로드 결과를 `editor.getContent()`의 HTML에서 찾았다. 하지만 티스토리의 이 메서드는 이미지를 자체 단축 표현으로 변환해서 내보냈다. 변환된 문자열을 다시 HTML로 파싱해도 기대한 `<img>`가 없었다.

**수정:**

1. `editor.getBody()`에서 실제 업로드된 이미지 요소를 찾도록 변경했다.
2. 이미지를 감싸는 `figure`와 티스토리 이미지 메타데이터를 함께 보존했다.
3. `data-mce-*`, `contenteditable` 등 편집기 내부용 속성은 복사본에서 제거했다.
4. 편집기 명령의 오류를 감싸서 어느 단계에서 실패했는지 앱에 전달하도록 했다.

**확인:** 복원된 `v0.3.0`→`v0.3.1` 소스 차이에서 수정 내용을 확인할 수 있다. 이후 편집기 검증에서도 파일 첨부와 본문 배치를 검사했다.

**교훈:** 편집기가 내보내는 저장 형식과 현재 화면의 이미지 요소가 같다고 가정하면 안 된다.

### T03. 태그를 입력한 뒤 저장 여부를 확인하는 기준이 실제 화면과 맞지 않음

**구분:** 발생·수정 / `0.3.1`~`0.3.2`

- 태그 입력과 완료 확인을 실제 티스토리 화면에 맞춰 보완했다.
- 초기 확인 방식은 태그 입력창의 부모 요소 텍스트에 태그가 있는지 보는 방식이었다.
- 이후 실제 화면의 태그 수정 링크에서 표시 텍스트·접근성 이름·제목을 확인하도록 변경했다.
- 입력창이 비워졌다는 사실만으로 성공으로 판단하지 않고, 해당 태그가 화면에 생성됐는지도 확인했다.

**검증 범위:** 오프라인 편집기 테스트에서 태그 입력을 확인한다. 실제 티스토리의 요소나 표시 방식이 바뀌면 다시 관찰하고 수정해야 한다.

### T04. 실제 공개 발행은 됐는데 앱에는 실패로 표시됨

**구분:** 발생·수정 / `0.3.2`

**증상:** 사용자가 요청한 글이 실제로 공개된 기록이 있었지만, 앱의 완료 확인 단계에서 오류가 났다.

**원인은 두 갈래였다.**

- 공개 발행 직후 페이지가 이동하면 편집기 안에서 실행하던 스크립트가 응답을 돌려주기 전에 끊길 수 있었다.
- 편집기에서 얻은 `/entry/...` 주소와 실제 공개 글의 숫자 주소가 다를 수 있었다. 예상 주소 하나만 확인하면 게시 결과를 놓쳤다.

**수정:**

1. 최종 제출 이후에는 편집기 스크립트 오류가 나더라도 공개 결과 확인을 진행한다.
2. 편집기 주소와 공개 RSS에서 찾은 같은 제목의 주소를 확인 후보로 모은다.
3. 대상 블로그의 글 주소인지 확인한다.
4. 로그인 세션 없이 공개 페이지를 읽고 제목·본문·사진이 요청한 내용과 맞는지 검증한다.
5. 제목이 같은 글이 목록에 있다는 이유만으로 발행 성공을 기록하지 않는다.
6. 제한 시간 안에 확인되지 않으면 재발행하지 않고 결과 불확실로 남긴다.

**교훈:** “버튼을 누르는 호출이 정상 종료됐는가”와 “서버에 글이 게시됐는가”는 별도로 확인해야 한다.

### T05. RSS에는 글이 있는데 실제 페이지는 없어 혼동이 생김

**구분:** 실제 상황 확인·사용자 결정 / `0.3.2` 시기

- 공개 목록에서 글이 보였지만 직접 접근한 페이지에서는 본문을 확인할 수 없는 상황이 있었다.
- 이후 사용자가 **직접 삭제했다**고 확인했다.
- 이를 앱의 미발행으로 간주해 자동으로 다시 올리면 사용자 삭제 의사를 거스르고 중복 게시할 수 있었다.
- 공개 목록, 실제 공개 본문, 로컬 발행 기록을 서로 구분하고 불확실한 상황에서 자동 재발행하지 않는 원칙을 유지했다.

**주의할 해석:** 당시 사용자 요청에 따른 실제 발행 기록은 있다. 다만 이후 삭제된 글이 현재도 공개돼 있다거나, RSS만으로 사진·본문 전체가 검증됐다고 쓰면 안 된다.

### T06. 발행 도중 종료·실패했을 때 재시도로 중복 게시될 위험

**구분:** 설계·보강

발행 결과 확인 오류를 다루면서, 실패 메시지를 보고 무조건 다시 제출하는 방식이 위험하다는 점이 분명해졌다.

**구현한 처리:**

- 버튼을 누른 시점의 제목·본문·사진을 별도의 발행 사본으로 고정한다.
- 최종 제출 직전에 제출 시각을 디스크에 기록한다.
- 제출 전에 실패하면 다시 시도할 수 있는 실패로 분류한다.
- 제출 후 실패하거나 앱이 종료되면 `uncertain`으로 분류하고 자동 재시도를 막는다.
- 같은 글 ID의 다른 입력 버전에도 이미 발행한 기록이 있는지 확인한다.
- 공개 본문을 확인한 경우에만 확인 기록인 `published-receipt.json`을 남긴다.
- 기존 편집기에 작성 중인 내용이 있으면 임의로 지우지 않는다.

**교훈:** 재시도 가능 여부는 오류 문구보다 실제 제출이 시작됐는지를 기준으로 결정해야 한다.

## 3. 사진·초안·표지·자료 폴더

### T07. Windows에서 “자료 폴더 열기”가 실패함

**구분:** 발생·수정 / `0.3.2`

**증상:** 앱의 자료 폴더 열기 버튼에서 오류가 났다.

**원인:** Codex를 통해 실행되는 Windows 환경에서 앱이 사용하는 경로 표현과 탐색기가 열 수 있는 실제 파일 시스템 경로 사이에 차이가 있었다. 자료가 사라진 문제가 아니라 폴더 열기에 전달한 경로의 문제였다.

**수정:** `fs.realpathSync.native(dataRoot)`로 실제 경로를 확인한 뒤 탐색기에 전달하도록 했다.

**남긴 기준:** 화면의 경로 문자열, 앱 실행 위치, 실제 자료 저장 위치를 구분한다. 실행 파일이 있는 폴더에 사용자 자료가 저장된다고 가정하지 않는다.

### T08. 사진을 제외하거나 순서를 바꿀 때 원본과 작성 입력을 구분해야 함

**구분:** 설계·보강

- `order.json`으로 활성 사진과 사용자 지정 순서를 관리한다.
- 화면에서 사진을 제외하는 동작은 원본 파일 삭제와 구분한다.
- 수집 중인 글은 자동으로 준비 완료 처리하지 않는다.
- 입력을 고정할 때 사진·메모 등의 내용을 기준으로 입력 버전을 계산한다.
- 같은 입력은 같은 출력 폴더를 재사용하고, 변경된 입력은 별도 버전으로 다룬다.
- 초안 생성 실패 시 이미 만들어 둔 초안과 사용자 편집을 보존한다.
- 사진의 실제 내용은 이미지 분석으로 확인하며, 파일명이나 OCR 추정만으로 글을 완성하지 않도록 작성 규칙을 정했다.

**의미:** 사진 선택 변경, 글 재생성, 원본 삭제는 서로 다른 작업이다. 이들을 하나의 동작으로 처리하지 않도록 했다.

### T09. 표지를 추가하면서 사진 중복·설명 유실·재생성 후 선택 유실을 막아야 함

**구분:** 기능 추가·설계 보강 / `0.3.4`

사용자는 기존 사진을 표지로 선택하거나 별도 표지를 업로드할 수 있게 요청했다.

**해결 방식:**

- 표지 선택은 `draft.cover`에 저장한다.
- 원래 본문 블록을 파괴적으로 재배열하지 않고, 공통 `articleBlocks` 함수에서 최종 배치를 계산한다.
- 앱·미리보기·발행이 같은 배치 함수를 사용한다.
- 기존 사진을 표지로 선택하면 설명을 유지하면서 맨 위로 옮기고 중복 삽입하지 않는다.
- 별도 표지는 원본 자료 폴더에 저장하지만 AI 분석용 사진 순서에는 자동으로 추가하지 않는다.
- 표지 파일의 해시·크기를 입력 사본에 기록하고 발행 사본에도 포함한다.
- 재생성 시 사용자 선택을 유지하되 민감한 사진으로 새로 분류되면 해제한다.
- 공개 글의 대표 이미지인 `og:image`를 확인하는 검증을 추가했다.

**검증 제한:** Node 테스트 35개와 오프라인 Electron 편집기 검증은 통과했다. 실제 티스토리 대표 이미지 설정 화면의 추가 확인은 브라우저 도구의 현재 주소 조회 문제로 중단됐다. 이 부분을 실제 서비스까지 검증 완료한 것으로 쓰면 안 된다.

### T10. 보관함에서 글을 지워도 관련 자료가 남으면 용량이 줄지 않는 문제

**구분:** 사용자 요청·설계 보강 / `0.3.3`

사용자는 로컬 초안이 차지하는 용량을 확인하고 필요 없는 글을 지울 수 있게 요청했다.

**구현한 범위:**

- 글별 자료 용량을 표시한다.
- 사용자가 삭제 확인 버튼을 누른 글 ID에 한해 원본 사진, 모든 입력 버전, 초안, 편집 이력, 발행 사본을 함께 삭제한다.
- 삭제 대상은 해당 글의 `inbox/<ID>`와 `drafts/<ID>`다.
- 생성·발행 중에는 삭제하지 못하게 한다.
- 실제 경로가 작업 공간 안인지, 링크를 통해 다른 폴더로 벗어나지 않는지 확인한다.
- 로컬 삭제는 티스토리 게시글 삭제와 분리한다.

**검증:** 임시로 만든 테스트 자료를 사용했다. 사용자 사진이나 초안을 삭제 테스트 대상으로 삼지 않았다.

## 4. AI 연결·말투·개발 화면

### T11. 제작자의 AI 환경에 의존하면 다른 사용자가 앱을 쓸 수 없음

**구분:** 사용자 요청·설계 보강 / `0.4.0`

다른 사용자는 자기 PC에서 자신이 로그인한 AI를 사용해야 했다.

**구현:**

- 도움말에서 Codex 또는 Claude Code CLI를 선택한다.
- 설치 여부와 로그인 여부를 구분해서 표시한다.
- 설치·로그인 명령을 복사할 수 있게 한다.
- 선택한 제공사를 초안 생성과 말투 분석에 동일하게 적용한다.
- 선택은 로컬 `ai.settings.json`에 저장하며 Git과 EXE에서 제외한다.
- 작업 중 제공사 변경을 막고, 실패했다고 다른 제공사로 몰래 전환하지 않는다.

**검증 제한:** 당시 두 CLI의 설치 상태를 확인했으나 Claude는 미로그인이었다. 연결 프로토콜은 테스트했지만 Claude 계정으로 실제 초안을 생성하는 전체 과정은 확인하지 못했다.

### T12. 이미지 경로 전달만으로는 Claude에 실제 사진이 전달되지 않음

**구분:** 연결 구현 보강 / `0.4.0`

- CLI마다 사진을 받는 방식과 결과를 돌려주는 방식이 달랐다.
- Claude에는 실제 이미지 바이트를 Base64 이미지 메시지로 전달하도록 했다.
- 결과도 일반 출력 문자열을 임의로 잘라 읽지 않고 구조화된 결과인 `structured_output`을 읽도록 했다.
- 큰 JSON이 여러 출력 조각으로 나뉘는 상황을 처리했다.
- 설치 안 됨, 로그아웃, 실행 실패, 결과 파싱 실패를 구분하도록 했다.

**검증:** 모의 CLI가 실제 PNG 바이트를 받았는지, 큰 한글 JSON을 여러 조각으로 출력해도 결과를 읽는지, 같은 선택이 말투 분석에도 적용되는지를 확인했다. 이 검사는 실제 유료 AI 생성 품질을 증명하지는 않는다.

### T13. 말투가 고정돼 있고 원하는 블로그 스타일을 직접 반영하기 어려움

**구분:** 사용자 요청·기능 개선 / `0.4.0`

**요청:** 말투 지침을 직접 수정하고, 원하는 블로그를 최대 3개까지 분석할 수 있어야 했다.

**구현:**

- 내 말투 설정에서 지침을 편집·저장한다.
- 최대 3개 공개 블로그의 글 본문을 수집해 선택한 AI로 분석한다.
- 분석에 참고한 글과 접근 실패를 표시한다.
- 분석 결과를 지침에 가져오거나 되돌릴 수 있게 한다.
- 기존 말투 이력을 보관한다.

**구분해야 할 점:** 말투 참고 블로그 3개는 글의 문장 스타일을 위한 설정이고, 사진 아래 참고자료 5개는 해당 글의 사실·배경을 보충하는 입력이다. 같은 기능이나 같은 개수 제한이 아니다.

### T14. 수정 확인마다 EXE를 빌드하는 방식이 느리고 혼란스러움

**구분:** 사용자 요청·개발 방식 개선

- 사용자는 화면 수정이 끝날 때까지 개발 모드로 확인하고 마지막에 빌드하기를 요청했다.
- 브라우저 앱은 `npm start`, 독립 개발 창은 `npm run desktop`으로 확인한다.
- EXE는 배포 시점에 만든다.
- 이미 실행 중인 서버나 Electron 메인 프로세스는 파일 변경만으로 새 코드를 읽지 않을 수 있으므로 해당 프로세스를 다시 실행해야 한다.

**교훈:** 수정한 소스, 현재 실행 중인 프로세스, 배포 EXE의 버전이 같은지 먼저 구분해야 한다.

### T15. 개발 앱을 켰는데 기존 배포 앱이 열리거나 어떤 화면인지 구분이 안 됨

**구분:** 발생·수정 / `0.4.0`

- Electron의 단일 실행 제한과 공용 사용자 데이터 경로 때문에 개발 실행과 기존 배포 앱을 구분하기 어려웠다.
- 개발 앱에 별도 사용자 데이터 경로를 지정하고 창 제목을 **H.Dev Studio · 개발 모드**로 고정했다.
- 기본 자료 위치도 개발과 배포를 구분했다.

| 실행 방식 | 기본 자료 위치 |
| --- | --- |
| 배포 앱 | `%APPDATA%/H.Dev Studio/workspace` |
| 개발 앱 | `%APPDATA%/H.Dev Studio Dev/workspace` |

별도 경로를 지정한 실행은 그 설정을 따른다. 개발 창의 자료가 배포 앱과 다르게 보인다고 곧바로 자료가 사라진 것으로 판단하면 안 된다.

### T16. 사이드바·색상·보관함이 원하는 사용감과 맞지 않음

**구분:** 사용자 피드백·UI 개선 / `0.4.0`

- 사이드바에 접기·펼치기와 작은 화면의 메뉴 열기·닫기를 추가했다.
- 보라색을 피하는 방향에서 청록색을 적용했지만, 사용자가 청록색도 선호하지 않았다.
- 사용자가 제공한 GitHub 라이트 화면을 기준으로 흰색·연회색 바탕, 진한 글자, 파란 링크, 초록색 주요 버튼, 주황색 선택 표시선으로 정리했다.
- 보관함의 빈 화면에 안내와 새 글 작성 버튼을 추가했다.
- 사용자가 선택한 글 쓰는 오리 이미지를 앱 로고와 브라우저·Windows 아이콘에 적용했다.

**기록상 구분:** 색상 변경과 로고 선택은 기능 오류가 아니라 디자인 방향을 구체화한 과정이다.

## 5. 참고자료 링크·공개 노션 읽기

### T17. 메모에 URL을 쓰면 AI가 링크 내용을 자동으로 읽는다고 기대함

**구분:** 기능 공백 확인·개선 / Unreleased

**사용자 질문:** “사진에 담기지 않은 이야기”에 참고 링크나 노션 주소를 남기면 글 작성에 반영하는가?

**기존 동작:** 메모는 AI에 전달됐지만, 메모 속 URL의 웹 본문을 앱이 가져오는 기능은 없었다. URL 문자열을 전달하는 것과 링크를 읽어 내용을 전달하는 것은 달랐다.

**개선:** 사진 아래에 별도 참고자료 영역을 만들고 링크 최대 5개와 본문 붙여 넣기를 지원했다. 공개 본문을 앱이 읽은 뒤 초안 생성 입력에 포함하도록 연결했다.

**현재 사용 흐름:** 사진·메모 입력 → 참고자료 추가 → 자료 읽기로 내용 확인 → 초안 생성.

### T18. 공개된 노션인데 초기 HTML만 읽어 본문을 못 가져옴

**구분:** 발생·수정 / Unreleased

**재현 자료:** 사용자가 제공한 [공개 ASIDE 가이드 노션 페이지](https://pickled-diascia-a8b.notion.site/ASIDE-76f5ca614672822796d18141433278b6?pvs=74).

**증상:** 브라우저에서는 긴 가이드가 정상적으로 보였는데 참고자료 읽기는 본문을 가져오지 못했다.

**원인:** 초기 구현은 HTTPS로 받은 HTML에서 본문을 추출했다. 해당 노션의 초기 응답은 약 20KB의 앱 화면 틀이었고, 제목은 `Notion`, 본문 초기 데이터는 비어 있었다. 실제 글은 브라우저가 뒤이어 요청하는 데이터에 들어 있었다.

**확인 과정:**

1. 공식 브라우저 조작 도구로 해당 공개 페이지가 열리는지 확인했다.
2. 브라우저에서는 본문이 보이므로 사용자 공개 설정 문제로 단정하지 않았다.
3. 노션 공개 웹 클라이언트의 코드와 응답 구조에서 본문 요청 방식을 확인했다.
4. 공개 페이지의 블록 데이터를 읽는 별도 처리기를 만들었다.

**사용한 요청:** 공개 웹 클라이언트가 사용하는 `POST /api/v3/loadCachedPageChunkV2`. 공개 페이지 ID와 이어 읽기 정보로 본문을 가져오며, 로그인 쿠키를 전달하지 않는다.

**해결 상태:** 해당 페이지의 공개 본문을 실제로 읽는 데 성공했다. 이 요청은 장기 호환성을 보장하는 공식 개발자용 API로 취급하면 안 되며, 노션 웹 클라이언트 변경에 맞춘 유지보수가 필요할 수 있다.

### T19. 첫 응답만 읽으면 긴 노션 문서 앞부분만 들어옴

**구분:** 발생·수정 / Unreleased

- 처음 받은 데이터에는 111개 블록과 다음 내용을 읽기 위한 커서가 있었다.
- 커서는 “다음 부분을 어디서부터 읽을지” 알려주는 값이다.
- 첫 응답을 전체 문서로 취급하면 뒷부분이 빠졌다.
- 응답의 커서와 필요한 `dedupeSessionId`를 이어 전달해 다음 부분을 수집하도록 했다.
- 여러 응답에 반복해서 등장하는 블록은 ID로 합치고, 문서의 부모·자식 순서에 따라 본문을 구성했다.

**추가 발견:** 7개 응답에서 618개 블록을 모은 뒤에도 문서에 연결된 자식 블록 39개가 없었다. 페이지 나누기 처리만으로 문제가 끝나지 않았다.

### T20. 페이지를 끝까지 받아도 접힌 제목·토글 속 내용이 누락됨

**구분:** 발생·수정 / Unreleased

**원인:** 접힌 항목의 자식 내용이 기본 페이지 요청에 모두 포함되지 않았다.

**수정:**

1. 문서의 부모 블록이 가리키는 자식 ID와 실제로 받은 블록을 비교한다.
2. 빠진 자식이 있으면 해당 공개 페이지 안의 부모 항목을 추가로 읽는다.
3. 서로 다른 블록 응답 포장 구조를 처리한다.
4. 제목, 목록, 코드, 표, 열 배치와 텍스트 안의 링크를 가능한 범위에서 유지한다.
5. 별도 하위 페이지나 데이터베이스를 무조건 따라가지는 않는다.
6. 반복 커서·순환 구조·누락된 내용·비공개 응답을 읽기 성공으로 표시하지 않는다.

| 추출 텍스트 | 26,191자 |
| 방문한 블록 | 657개 |
| 길이 제한으로 잘림 | 없음 (`truncated: false`) |
| 뒷부분 확인 | 27번·28번 섹션, 공식 자료 모음, 마지막 요약 포함 |
| 내용 구조 | 접힌 항목, 표, 코드, 본문 링크 포함 |

이 숫자는 당시 수집한 페이지 버전의 결과다. 이후 원문이 수정되면 달라질 수 있다. 블록 수와 문자 수는 텍스트 수집 결과이며, 노션에 첨부된 모든 이미지의 시각적 내용을 분석했다는 뜻은 아니다.

### T21. 긴 문서가 잘리거나 읽기 실패를 성공으로 오해할 수 있음

**구분:** 발견에 따른 보강 / Unreleased

**적용한 제한과 표시:**

| 입력 | 현재 제한 |
| --- | --- |
| 글별 참고자료 | 최대 5개 |
| 직접 붙여 넣은 자료 | 자료당 10,000자 |
| 일반 웹 본문 | 자료당 10,000자 |
| 공개 노션 본문 | 자료당 60,000자 |

- 긴 노션은 일반 웹 본문과 다른 길이 제한을 적용했다.
- 제한 때문에 일부만 사용하는 경우 잘림 여부를 표시한다.
- 반복 요청에는 횟수와 시간 제한을 두어 끝없이 기다리지 않게 했다.
- 직접 붙여 넣은 자료는 웹 요청을 생략하고 직접 입력 상태로 구분한다.
- 접근하지 못한 자료에는 추측한 본문을 채우지 않는다.

**남은 제한:** 비공개·로그인 필요 페이지를 사용자 세션으로 읽는 기능은 없다. 일반적인 JavaScript 사이트 전체에 브라우저 렌더링을 제공하는 구현도 아니다. 노션은 별도 지원한 사례다.

### T22. 링크를 넣었어도 무엇을 읽었는지 사용자가 확인하기 어려움

**구분:** 사용자 불편에 따른 개선 / Unreleased

- 초안 생성 전에 누를 수 있는 **자료 읽기** 버튼을 추가했다.
- 제목, 읽은 글자 수, 본문 미리보기, 읽기 실패 이유를 표시한다.
- 자료를 읽는 중이거나 초안을 생성하는 동안 관련 입력을 잠가 작업 중 입력이 바뀌지 않게 한다.
- 링크 중복·개수 제한·직접 입력·삭제·자동 저장·다시 열기를 검사했다.
- 초안 생성 시에는 현재 공개 본문을 다시 읽어 AI 입력으로 전달한다.
- 읽은 자료와 확인 시각을 초안 자료로 보관한다.

**검증:** 실제 노션 페이지를 읽고, 앱 화면에서 결과를 표시한 뒤, 읽은 내용을 테스트용 생성 함수가 전달받는 경로까지 확인했다. 실제 AI가 그 자료로 최종 글을 얼마나 잘 쓰는지는 별도 검증이다.

### T23. 참고자료가 바뀌어도 같은 입력으로 취급되거나 기존 초안을 잃을 위험

**구분:** 설계·보강 / Unreleased

- 참고자료를 입력 버전 계산에 포함했다.
- 참고자료가 없는 기존 글의 입력 식별값은 불필요하게 바뀌지 않도록 했다.
- 생성 실패 시 기존 초안을 유지하고, 성공적으로 읽은 자료의 확인 기록을 보존하도록 했다.
- 웹페이지 안의 문장은 글의 참고 내용으로 취급하며 앱이나 에이전트의 실행 지시로 사용하지 않도록 했다.
- 공개 HTTPS 주소만 읽고, 인증 정보가 들어간 주소·내부망 주소·우회되는 이동 등을 차단하도록 공통 웹 읽기를 보강했다.

**현재 동작의 경계:**

- 참고자료를 추가했다고 이미 생성한 글이 저절로 다시 작성되지는 않는다. 반영하려면 새로 생성해야 한다.
- 참고 링크는 작성 근거로 전달된다. 발행 본문 하단에 출처 목록을 자동 삽입하는 별도 기능과는 구분된다.
- 링크 안의 이미지 내용까지 필요하면 해당 이미지를 사진 입력으로 추가해야 한다.

## 6. Git 이력·개인정보·빌드 정리

### T24. 버전별 EXE는 있는데 과거 Git 개발 이력이 없었음

**구분:** 발생·복원

**요청:** 저장소를 만들고 이전 버전부터 순서대로 소스를 올리되, 용량을 차지하는 과거 빌드는 정리하고 싶다는 요청이었다.

**문제:** 과거 개발 커밋이 없어서 단순히 현재 소스에 옛 버전 태그만 붙이면 부정확한 이력이 됐다.

**복원:**

- `v0.3.0`~`v0.3.4` 배포본의 `app.asar`와 별도로 배포된 파일에서 소스를 추출했다.
- 버전별로 소스를 확인하고 순서대로 커밋·태그를 만들었다.
- 원본 아카이브와 파일 해시를 복원 기록에 남겼다.
- `0.2.0`은 소스가 없어 기능 변경 기록만 남겼다.
- 배포본에 없는 당시 테스트와 개발 설정까지 복구됐다고 주장하지 않았다.
- 개발용 패키지 설정과 잠금 파일의 보완 범위를 문서화했다.

**교훈:** 과거 배포 상태를 복원한 이력과 실제 개발 당시의 커밋 이력을 명확히 구분해야 한다.

### T25. 과거 빌드 폴더의 소스가 실제 해당 버전과 달랐음

**구분:** 발생·수정 / `0.3.1` 복원 중

- 기존 `0.3.1` 빌드 폴더의 발행 코드가 이후 수정된 내용으로 바뀌어 있었다.
- 폴더 이름만 믿고 복원했다면 다른 버전의 코드를 `0.3.1`로 기록할 수 있었다.
- 해당 버전의 원본 EXE에서 다시 추출했다.
- 배포 아카이브의 무결성 정보와 파일 해시를 비교했다.
- 따로 분리된 `desktop/publish.mjs`도 복원 대상에 포함했다.

**교훈:** 변경 가능한 작업 폴더보다 원본 배포 아카이브와 해시를 기준으로 삼아야 한다.

### T26. 공개 저장소·공유 EXE에 제작자의 개인 설정이 섞일 수 있음

**구분:** 점검·수정 / 이력 정리 및 `0.4.0`

- 공유 소스의 개인 블로그 기본 링크와 표시 이름을 공용 값으로 바꿨다.
- EXE에는 공용 `config/` 템플릿만 포함하도록 했다.
- 기존 PC의 블로그 설정·말투는 초기 설정 과정에서 덮어쓰지 않는다.
- 개인 설정, 말투 원문, 사진, 초안, 로그, 로그인 자료와 EXE를 Git에서 제외했다.
- 새 사용자가 자기 환경을 만들 수 있도록 `npm run setup`과 안내를 추가했다.
- 배포본 검사에서 개인 자료가 포함되지 않았는지 확인했다.

**교훈:** Git 제외 설정과 EXE 포장 대상은 별개로 확인해야 한다. Git에서 제외했다고 배포 파일에서도 자동 제외되는 것은 아니다.

### T27. Git 작성자 정보를 고쳐도 과거 커밋 객체가 원격에서 보일 수 있었음

**구분:** 발생·사용자 결정 / 잔여 사항 있음

**상황:** 공개 브랜치와 태그의 작성자를 프로젝트 이름과 GitHub `noreply` 주소로 정리했지만, 이전 커밋의 직접 주소에서는 개인 이메일이 조회되는 문제가 당시 확인됐다.

**원인:** 현재 브랜치에서 도달할 수 없게 만든 과거 커밋 객체가 원격 서비스에서 즉시 없어지는 것은 아니었다.

**당시 결정:** 저장소 재생성 방안까지 설명했으나 사용자가 **현재 상태로 유지**하기를 선택했다. 저장소는 그 결정에 따라 유지했다.

**기록상 주의:**

- “현재 브랜치·태그의 작성자 정보 정리”와 “과거 원격 객체까지 완전히 삭제”를 같은 완료로 표현하면 안 된다.
- 이 문서에는 개인 이메일과 문제가 된 과거 직접 주소를 재기록하지 않는다.
- 당시 남은 사항을 기록한 것이며, 문서 작성 중 원격의 현재 노출 상태를 다시 검사한 것은 아니다.

### T28. 여러 작업이 같은 폴더를 수정해 배포·커밋 범위가 섞일 위험

**구분:** 실제 작업 충돌 위험 조정

- 화면·말투 개선과 Git 복원·공개·빌드 정리가 같은 작업 폴더에서 진행됐다.
- 다른 작업의 수정 파일을 되돌리거나 의도하지 않은 변경을 배포에 섞을 위험이 있었다.
- 담당 범위를 나누고 커밋·푸시·빌드 시점을 조율했다.
- 공유할 소스를 별도로 준비하고 그 사본에서 검사했다.
- 다른 작업의 미완료 변경을 임의로 덮어쓰지 않았다.

**교훈:** 동시에 편집할 수 있다는 사실과 동시에 같은 소스를 배포해도 된다는 것은 다르다. 배포 대상 파일을 고정해 확인해야 한다.

### T29. 중간 빌드와 복원용 폴더가 쌓여 디스크를 많이 사용함

**구분:** 사용자 요청·정리

- 반복 빌드, `win-unpacked`, 과거 EXE, 소스 복원용 임시 폴더가 누적됐다.
- 과거 소스는 Git 커밋·태그로 보관하고 로컬 EXE는 최신 버전 하나를 남기는 기준으로 정리했다.
- 삭제 전 최신 EXE 해시, 백업된 소스, 대상 폴더를 확인했다.
- 사진·초안·설정은 정리 대상에 넣지 않았다.

**당시 결과:** 사용자가 실행 결과로 `Removed bytes: 2468099461`을 전달했다. 약 **2.47GB**를 정리했고 당시 최신 `0.3.4` EXE를 보존했다.

**시점 구분:** 이후 `0.4.0` 빌드에서 중간 파일 자동 정리가 다시 차단된 기록은 별개다. 앞선 2.47GB 정리가 성공했다고 모든 후속 임시 폴더까지 없어졌다고 볼 수는 없다.

### T30. 자동 삭제가 실행 환경의 승인 정책에 막힘

**구분:** 도구 실행 제한

- 빌드·검증용 파일 정리 시 자동 승인 검토가 삭제 작업을 차단한 기록이 여러 번 있었다.
- 차단된 작업은 삭제 성공으로 보고하지 않았다. 일부 임시 파일은 그대로 남았다.
- 과거 빌드 정리에서는 대상과 보존 파일을 확인할 수 있는 PowerShell 스크립트를 준비해 사용자가 직접 실행할 수 있게 했다.
- 해당 스크립트는 기본 실행에서 대상만 보여주고, 적용 옵션에서 실제 삭제하도록 했다.

**주의:** 이는 당시 실행 환경의 정책 차단 기록이다. 파일이 손상됐거나 앱 삭제 기능 자체가 실패했다는 뜻은 아니다. 정책이 상세 이유를 제공하지 않은 경우 임의의 이유를 붙이지 않았다.

### T31. 정리 스크립트가 한글 파일명 때문에 경로 오류를 냄

**구분:** 발생·수정

**실제 오류:** `GetFullPath` 호출 중 “경로에 잘못된 문자가 있습니다.”

**원인:** Windows PowerShell이 스크립트의 인코딩을 잘못 해석하면서 한글이 들어간 정리 대상 경로가 깨졌다.

**수정·검증:**

- 스크립트를 UTF-8 BOM 형식으로 저장했다.
- 같은 PowerShell 환경에서 삭제 대상 미리보기를 다시 확인했다.
- 실행 경로의 폴더 구분도 바로잡았다.
- 경로 문제가 해결되기 전에는 삭제를 진행하지 않았다.

**교훈:** 한글 경로를 다루는 스크립트는 편집기의 표시만 확인하지 말고 사용자가 실행할 셸에서 검사해야 한다.

### T32. 실행 중인 앱이 정리 대상 폴더를 사용해 삭제가 중단됨

**구분:** 발생·정상 보호 동작

- 수정한 정리 스크립트가 사용 중인 실행 파일을 발견해 중단했다.
- 앱 메인 창과 티스토리 창을 종료한 뒤 다시 실행하도록 안내했다.
- 실행 중인 프로세스가 있는 상태에서 강제 삭제하지 않았다.
- 이후 사용자 실행 결과로 정리 성공을 확인했다.

**주의:** 당시 정리 스크립트는 `0.3.4` 파일과 해시를 기준으로 만든 일회성 대상 목록이다. 현재 버전의 범용 정리 명령으로 그대로 재사용하면 안 된다.

### T33. 버전·EXE·문서가 어긋나거나 같은 이름의 배포본이 바뀔 위험

**구분:** 설계·보강

- `package.json`, 잠금 파일, 변경 내역의 버전을 맞추도록 했다.
- 기존 버전 EXE 덮어쓰기를 막았다.
- 배포 정보와 SHA256 확인 파일을 생성하도록 했다.
- GitHub Windows 검사와 수동 EXE 빌드 절차를 마련했다.
- 실제 `0.4.0` EXE를 실행하고 포함된 앱 소스·로고·공용 설정을 확인했다.
- 소스 수정 때마다 빌드하지 않고 개발 확인 후 배포 시 빌드하는 기준을 문서화했다.

## 7. 검증 도구에서 발생한 문제

### T34. Electron 검증 스크립트가 준비 완료를 기다리며 멈춤

**구분:** 검증 코드 문제·수정

- 검증용 Electron 진입 파일에서 최상위 `await app.whenReady()`로 대기하는 구조가 시작을 막는 문제가 있었다.
- 준비 대기를 비동기 `run()` 함수 안으로 옮겨 호출하도록 바꿨다.

**구분:** 앱 기능의 실패와 앱을 검사하는 스크립트의 시작 실패를 혼동하지 않아야 한다.

### T35. 숨긴 창·작은 화면의 검증이 실제 기능 상태를 제대로 보여주지 못함

**구분:** 검증 환경 보완

- 화면 밖 Electron 창에서는 백그라운드 제한이 검사 진행에 영향을 줄 수 있어 검증 창에 `backgroundThrottling: false`를 적용했다.
- 작은 화면 캡처에서 열린 사이드바가 참고자료 영역을 덮었다.
- 사이드바 상태를 맞추고 해당 영역으로 이동한 뒤 화면을 확인하도록 검증 순서를 보완했다.

**교훈:** 화면이 가려져 있는 것과 기능이 없는 것을 구분하고, 캡처 전에 창 크기·메뉴 상태를 확인해야 한다.

### T36. 브라우저·Windows 자동 조작 도구 오류로 실제 화면 확인이 중단됨

**구분:** 검증 제한

기록된 사례는 다음과 같다.

- 실제 티스토리 표지 설정 확인 중 브라우저의 현재 URL을 읽는 단계가 실패했다.
- Windows 입력 도구가 `CacheRequest` 속성 관련 오류를 냈다.
- 창 위치·크기가 바뀐 뒤 이전 화면 정보를 이용한 클릭은 “window bounds changed” 오류로 거절됐다.

**대응:** 도구가 확인하지 못한 클릭이나 입력을 완료했다고 주장하지 않았다. 가능한 범위는 별도 Electron 검증으로 확인하고, 실제 서비스에서 추가 확인이 필요한 부분을 남겼다.

**교훈:** 도구 오류를 앱 오류로 단정하지도, 모의 검사 통과를 실제 화면 조작 성공으로 확대하지도 않아야 한다.

### 남아 있는 제약·추가 확인 사항

1. **Claude 실제 생성:** 당시 로그인되지 않아 실제 계정으로 사진 분석부터 최종 초안까지의 실행은 확인하지 못했다.
2. **참고자료 기반 실제 글 품질:** 공개 노션 읽기와 생성 입력 전달은 확인했지만, 그것만으로 AI의 사실 반영·말투·출처 작성 품질까지 보장하지는 않는다.
3. **실제 티스토리 표지:** 대표 이미지 관련 코드와 모의 검사는 있으나 실제 설정 화면의 추가 검증은 중단된 상태로 기록돼 있다.
4. **노션 지원 범위:** 공개 페이지의 텍스트를 지원한다. 비공개 페이지, 모든 하위 페이지·데이터베이스, 첨부 이미지의 시각적 내용까지 자동 수집하는 기능은 아니다.
5. **노션 호환성:** 공개 웹 클라이언트의 내부 요청 방식이 바뀌면 수정이 필요할 수 있다.
6. **일반 웹페이지:** 본문이 로그인 뒤에 있거나 JavaScript 실행 후에만 나타나는 사이트는 일반 HTML 읽기로 해결되지 않을 수 있다. 본문 직접 입력을 사용할 수 있다.
7. **이전 초안:** 참고자료를 새로 추가한 뒤에는 다시 생성해야 새 내용이 반영된다.
8. **본문 출처 목록:** 참고 링크 수집과 발행 글 하단의 자동 출처 목록 생성은 별도 기능이다.
9. **과거 Git 객체:** 당시 개인 이메일 잔여 노출 문제는 사용자 결정으로 저장소를 유지했다. 현재 원격 상태를 이 문서에서 새로 검증하지 않았다.
10. **배포 반영:** 최신 참고자료·노션 개선은 개발 소스 상태다. EXE 반영 여부는 다음 배포의 변경 내역과 포함 소스로 확인해야 한다.
11. **후속 빌드 임시 파일:** 과거 2.47GB 정리 성공과 이후 빌드 정리 차단은 별개다. 현재 남은 파일을 확인하지 않고 전체 정리 완료로 간주하면 안 된다.
