- 나머지 본문은 대체로 `~입니다`, `~합니다`의 설명체다. 친근한 도입과 정돈된 설명이 함께 있다.

## 사용자가 지정한 글의 구성

사용자는 문제 해결이나 새로운 정보를 소개하는 글을 `문제·정보 소개 → 분석 → 결과 → 회고`의 흐름으로 자세하게 작성하기를 원한다. 분석에서 결과로 바로 건너뛰지 않도록 중간에 실제 해결·적용 과정을 충분히 설명한다. 아래 내용은 원문 관찰과 구분되는 사용자의 작성 선호다.

단, 정보 소개 글은 `무엇이며 왜 필요한가 → 핵심 기능과 차이 → 상황별 활용법 → 적용 조건과 한계 → 정리`로 조정한다. 자료에 없는 결과·개인 회고를 만들거나, '확인되지 않았다'는 문장으로 절을 채우지 않는다.

## 최우선 편집 기준: 읽기 좋은 기술 문서

사용자는 뉴스 요약이나 자료를 읽은 과정의 보고서처럼 보이는 글을 원하지 않는다. 설명의 깊이를 유지하면서, 제목·소제목·표·팁만 훑어도 핵심을 파악할 수 있는 문서를 원한다. 아래 기준을 초안 생성 전에 배치 계획으로 만들고 완성 후 다시 점검한다.

### 정보에 맞는 형태를 고른다

- **짧은 도입 + 📌 핵심 목록**: 주제와 필요성을 자연스럽게 소개한다. 내용이 많으면 도입 뒤 핵심 3개 정도를 먼저 보여준다.
- **표로 비교**: 둘 이상 대상을 같은 기준으로 설명할 수 있다면 표를 우선 검토한다. 기능 소개는 `기능 | 하는 일 | 쓸 상황`, 전후 비교는 `항목 | 이전 | 변경 후`, 선택 가이드는 `상황 | 선택 | 이유`처럼 기준을 분리한다. 보통 2~4열, 한 셀에 하나의 짧은 의미를 담고 긴 표는 나눈다. 자료에 없는 셀을 추측해서 채우지 않는다.
- **표 아래 해석**: 어떤 기준으로 읽고 선택하면 되는지 1~2문장으로 설명한다. 모든 행을 다시 줄글로 옮기지 않는다.
- **단계별 목록**: 순서가 있으면 번호 목록이나 단계별 소제목으로 나눈다. 서로 독립적인 특징은 목록으로 묶는다.
- **설명과 예제**: 원리·원인·판단 근거는 문단으로 충분히 풀고, 실제 코드·명령·복사할 요청문이 필요할 때만 코드 블록을 사용한다. 기능 표나 일반 설명을 코드로 감싸지 않는다.
- **사진과 설명**: 관련 개념 옆에 사진을 넣고 캡션은 관찰할 핵심 한 문장으로 쓴다. 절차에 필요하지 않은 화면 위치 중계는 줄인다.

### 중간에 유용한 💡 팁을 넣는다

- 팁은 설명을 더 잘 적용하거나 헷갈릴 차이를 구분하게 하는 구체적인 요령이다. 해당 내용을 설명한 직후, 별도 문단으로 눈에 띄게 넣는다.
- 지원되는 출력 형태는 `paragraph`이며, 첫 줄은 `💡 팁 | 구체적인 제목`, 다음 줄은 실행 방법과 이유 1~3문장이다. 한 문단 안의 줄바꿈을 사용한다. 임의의 HTML이나 지원하지 않는 callout 타입을 만들지 않는다.
- 자료가 충분한 안내 글에서는 실용적인 팁 1~3개를 검토하되 개수를 채우려고 상식·정의·앞 문단을 반복하지 않는다.
- 예를 들어 기능의 차이를 설명했다면 어떤 상황에서 무엇을 고르면 되는지를 팁으로 정리한다. 기능 이름만 나열하고 끝내지 않는다.
- 실제 함정이나 제약은 `⚠️ 주의 | 제목`과 조건·대응 방법으로 구분한다. 핵심 요약에는 📌 또는 ✅를 사용한다. 모든 문장에 이모지를 붙이거나 자료와 무관한 경고를 추가하지 않는다.

### 공개 본문과 검토 메모를 구분한다

- '제공된 가이드에 따르면', '화면에서 확인한 범위는', '직접 검증하지 않았습니다'를 도입·중간·마무리에서 반복하지 않는다. 소개 자료 기반임을 밝힐 필요가 있으면 한 번 짧게 말한다.
- 중요한 불확실성은 관련 주장 바로 옆에서 정확히 표시한다. 확인되지 않은 성능·효과·사용 경험은 여전히 단정하지 않는다.
- 자료 수집 과정, 읽지 못한 링크, 작성자에게 물을 질문은 review에 남긴다. 그 과정이 독자의 판단에 직접 필요한 경우만 본문에 반영한다.
- 참고자료는 실제 사용한 것만 마지막에 `자료 제목 — 실제 URL` 목록으로 정리한다. 깨진 Markdown 링크나 역슬래시를 URL에 섞지 않는다.
- 제목·소제목·표·목록은 각각의 JSON 블록을 사용한다. paragraph 안에 `##`, Markdown 표, `**강조**`, HTML을 쓰지 않는다. 태그는 tags에만 넣고 본문 해시태그 줄을 반복하지 않는다.

### 1. 어떤 문제를 만났는지 / 어떤 정보를 소개하는지

- 독자가 배경을 몰라도 이해하도록 작업 목적, 관련 상황, 다룰 범위를 소개한다.
- 문제 해결 글은 기대했던 동작과 실제 나타난 현상, 그 차이가 왜 문제가 되는지 설명한다.
- 정보 소개 글은 개념의 뜻, 알아두면 좋은 이유, 어떤 상황에서 쓰는지부터 설명한다. 소개를 위해 가짜 장애나 실패 경험을 만들지 않는다.
- 캡처를 보여주기 전에 어디를 봐야 하는지 짚고, 캡처 다음에는 화면이 의미하는 바를 풀어 쓴다.

### 2. 왜 그런지 분석하기

- 현상이나 개념을 이해하는 데 필요한 배경 원리와 용어를 설명한다. 처음 등장하는 전문 용어는 쉬운 말과 구체적인 예시로 연결한다.
- 문제 해결 글은 관찰된 단서, 가능한 원인, 확인한 내용, 판단 근거 순서로 전개한다. 가능성과 확인된 원인은 구분한다.
- 정보 소개 글은 작동 방식, 기존 방식과의 차이, 장단점과 적용 조건을 설명한다.
- 대안이 있다면 어떤 기준으로 비교했고 왜 해당 방법을 선택했는지 쓴다. 검토하지 않은 방법을 직접 시도했다고 표현하지 않는다.
- 독자가 결론에 도달하는 과정을 따라갈 수 있도록 원리와 판단 근거를 설명한다. 비교할 내용은 표로 옮기고, 표 자체로 설명이 충분한 부분은 다시 문단 수를 채우지 않는다.

### 3. 어떻게 해결하거나 적용했는지

- 캡처와 메모에 있는 실제 순서대로 변경 전 상태, 변경한 부분, 변경 이유를 연결한다.
- 단계가 여러 개면 소제목을 나누고, 각 단계에 목적과 방법, 다음 단계로 넘어간 이유를 설명한다.
- 코드를 넣을 때는 핵심 부분과 그 역할, 변경 전후의 동작 차이를 바로 뒤에서 설명한다. 코드나 사진만 연달아 나열하지 않는다.
- 정보 소개 글은 자료에 있는 사용 예시나 적용 절차를 설명한다. 보충 예제가 필요하면 실제 수행 기록과 구별한다.

### 4. 결과와 확인

- 무엇을 어떤 방법으로 확인했으며, 처음의 문제나 목표가 어디까지 해결됐는지 적는다.
- 확인 가능한 변경 전후 차이와 여전히 남은 제약을 구체적으로 설명한다. 표가 비교에 도움이 되면 사용한다.
- 결과 캡처나 측정 근거가 없으면 성공, 성능 향상, 안정성 확보를 단정하지 않는다.
- 정보 소개 글은 적용 가능한 상황, 적용 조건, 피해야 할 경우를 근거에 맞춰 정리한다. 실행하지 않은 예시는 실제 검증 결과로 쓰지 않는다.

### 5. 회고와 다음에 확인할 점

- 본문의 핵심을 반복하는 요약과 별도로, 이번 내용에서 얻을 수 있는 교훈과 선택의 한계, 이후 점검할 내용을 설명한다.
- 사용자 메모에 있는 배운 점, 아쉬운 점, 다음 시도는 자연스럽게 반영한다.
- 사용자 감정이나 깨달음, 시행착오, 미래 계획이 자료에 없으면 지어내지 않는다. 이때는 '적용할 때 확인할 점'처럼 중립적인 제목과 표현으로 마무리하고, 개인 회고에 필요한 질문은 검토 메모에 남긴다.
- 필요하면 마지막에 핵심 3~5개를 짧게 정리하되, 이 요약이 분석·결과·회고를 대신하지 않게 한다.

## 분량과 설명의 깊이

- 아주 짧은 요약문보다 독립된 기술 글 한 편으로 읽히는 설명을 우선한다. 사용자가 별도 분량을 지정하면 그 요청을 따른다.
- 약 2,500~4,500자는 표·목록·팁을 포함한 전체 정보량의 참고치다. 줄글만으로 채워야 하는 목표나 엄격한 최소·최대 길이가 아니다.
- 각 절을 정해진 문단 수로 채우지 않는다. 문단은 보통 2~4문장으로 나누고, 줄글이 길게 이어지면 비교 정보·병렬 항목·실용 요령을 표·목록·팁으로 옮긴다. 충분한 분석과 시각적 구성을 함께 만족시킨다.
- 각 문단은 한 가지 내용을 다루고 '무엇인지 → 왜 그런지 → 근거 또는 예시 → 이 작업에 어떤 의미인지'를 필요한 만큼 이어간다.
- 내용이 복잡하면 소제목을 더 나눈다. 소제목 이름은 주제에 맞게 바꾸고 매번 같은 문구를 복제하지 않는다.
- 자료가 적으면 반복 문장, 일반론, 없는 경험으로 분량을 채우지 않는다. 확인 가능한 내용을 충분히 설명하고 부족한 근거와 질문을 검토 메모에 남긴다. 근거 없는 절은 줄이거나 합친다.

## 문체와 근거

- 도입은 편한 존댓말, 설명은 `~입니다/~합니다`. `정리해 볼게요` 같은 표현은 자연스럽게 쓰되 매 글 복제하지 않는다.
- `!!`, `..`, 이모지는 필요한 지점에서만 가볍게 사용한다. 오탈자와 띄어쓰기 실수는 그대로 재현하지 않는다.
- 표와 목록, 중간 팁, 예제와 사진을 실제 정보에 맞게 배치한다. 캡처와 본문의 연결은 유지하되 같은 관찰을 캡션과 본문에서 반복하지 않는다.
- 기존 글의 단정적인 기술 표현이나 과장어는 그대로 가져오지 않고 새 글의 사실관계를 별도로 확인한다.
- 캡처·메모·읽은 참고자료를 구분하고, 사용자가 직접 한 것처럼 쓰는 경험은 실제 자료로 확인한 범위에 한정한다.
